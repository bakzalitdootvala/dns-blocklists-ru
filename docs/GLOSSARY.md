Определения относятся к этому проекту. У каждого термина указано, что он
означает в нашей сборке или при работе DNS. Примеры `ads.example.org` и
`203.0.113.20` учебные: они не являются утверждением о вредоносности адреса.

## Один запрос от приложения до результата

Приложение хочет подключиться к `ads.example.org` и спрашивает у AdGuard Home его IP.
AdGuard сверяет имя с доменными правилами `combined.txt`. Если имя запрещено,
возвращает ответ блокировки. Иначе запрашивает внешний DNS-сервер и проверяет
полученные адреса по IP-правилам того же файла. Совпавший запрещённый IP также
блокирует ответ. При разрешённом результате приложение получает адрес и само
устанавливает соединение. DNS-сервер не скачивает вместо него страницу сайта.

Сборка правил происходит отдельно: списки источников и региональные дополнения
проверяются, объединяются в `combined.txt`, а сведения об их происхождении и
контрольная сумма файла записываются в `manifest.json`. AdGuard читает фильтр;
проверяющий скрипт читает и фильтр, и манифест.

## DNS и программы

### DNS, DNS-запрос и DNS-ответ

**DNS — Domain Name System, система доменных имён.** Она хранит разные сведения
об именах; поиск IP — один из видов запроса. Вопрос «какой IPv4 у ads.example.org?»
является DNS-запросом типа A. DNS-ответ содержит записи или код результата.

### Домен, поддомен, hostname и apex

**Доменное имя** — имя в DNS, например `example.org`. `ads.example.org` — его
**поддомен**. **Hostname** в наших функциях — конкретное проверяемое DNS-имя.
**Apex** относительно правила — само базовое имя без добавленного поддомена:
для правила на `ads.example.org` apex — `ads.example.org`, потомок — `a.ads.example.org`.

### DNS-сервер, resolver и upstream DNS

**DNS-сервер** — программа, принимающая DNS-запросы. **Resolver (резолвер)** получает
ответ для клиента из кэша либо с помощью других DNS-серверов. **Upstream DNS** —
вышестоящий DNS-сервер, которому наш AdGuard передаёт разрешаемый запрос.
Это другое значение слова upstream, чем исходный Git-репозиторий Mullvad.

### AdGuard Home и AdGuard DNS

**AdGuard Home** — установленная пользователем программа DNS-сервера с фильтрацией,
веб-интерфейсом и журналом запросов. Она читает наш `combined.txt`.
**AdGuard DNS** — отдельный DNS-сервис компании AdGuard. Использование программы
AdGuard Home не означает, что внешним DNS обязательно выбран сервис AdGuard DNS.

### BIND и bind9-utils

**BIND — Berkeley Internet Name Domain**, другая программа DNS-сервера. Она умеет
обслуживать DNS-зоны и выполнять разрешение имён; блокировку можно настроить через RPZ.
**bind9-utils** — пакет вспомогательных утилит BIND, включая `named-checkzone`
для проверки файлов зон.

### DNS-запись и типы A, AAAA, CNAME

**DNS-запись** — структурированное утверждение об имени. **A** связывает имя с IPv4,
**AAAA** — с IPv6. **CNAME (Canonical Name)** указывает другое доменное имя,
по которому нужно продолжить разрешение. Например, имя рекламы может ссылаться
через CNAME на другое имя, ответ которого содержит запрещённый IP.

### DNS-зона, SOA, NS и IN

**DNS-зона** — набор DNS-записей, обслуживаемый как единое целое. Файл `.zone`
содержит эти записи в текстовом формате. **SOA (Start of Authority)** задаёт
служебные сведения и параметры зоны; **NS (Name Server)** указывает её DNS-сервер.
**IN (Internet)** — класс записи. Например, `example.org IN A 203.0.113.20`
задаёт IPv4-адрес имени в этом классе.

### RPZ и запись CNAME на точку

**RPZ — Response Policy Zone, зона политики ответов.** BIND использует её для
изменения ответов по правилам, например для блокировки имени. В контексте RPZ
`CNAME .` означает политику ответа NXDOMAIN. Точка обозначает корень DNS;
нельзя переносить это специальное значение на произвольную обычную CNAME-запись.

### named-checkzone

Утилита BIND, которая разбирает файл зоны и проверяет синтаксис и согласованность
записей, как при загрузке зоны DNS-сервером. Не ищет вредоносные сайты и не
сравнивает список с интернетом. Корректно оформленная ложная блокировка пройдёт
эту проверку. Наш `combined.txt` имеет другой формат и ею не проверяется.

### RCODE, NOERROR, NXDOMAIN, NODATA и SERVFAIL

**RCODE (Response Code)** — код результата в DNS-ответе. **NOERROR** означает
отсутствие DNS-ошибки; **NXDOMAIN** — что имя не существует; **SERVFAIL** — что
сервер не смог обработать запрос. **NODATA** — ситуация, когда имя существует,
но запрошенного типа записи нет; это не отдельный RCODE. Например, обычный сайт
может иметь A и возвращать NOERROR без AAAA. Наш тест проверяет оба типа отдельно.

### TTL и кэш DNS

**TTL — Time To Live**, срок хранения записи в кэше в секундах. **Кэш** — сохранённый
ответ для повторного использования без нового обращения к источнику. В живом
тестовом AdGuard кэш ответов выключен, чтобы проверка отключения фильтра не
получала прежний сохранённый результат.

### DoH, HTTPS, TLS и bootstrap DNS

**DoH — DNS over HTTPS**, передача DNS-запроса внутри HTTPS. Сам протокол
не требует блоклистов: фильтрацию отдельно выполняет принимающий DNS-сервер. **HTTPS** — HTTP
с защищённым соединением **TLS (Transport Layer Security)**. TLS проверяет
сертификат сервера и защищает передаваемые данные. **Bootstrap DNS** нужен,
чтобы сначала узнать IP внешнего DNS, если его адрес задан именем. Тестовый
стенд использует URL Google с IP, поэтому для него этот предварительный поиск не нужен.

### HTTPS record и IP hints

**HTTPS record** — отдельный тип DNS-записи, описывающий параметры подключения
к HTTPS-сервису. Это не сама веб-страница и не ответ HTTP. Поля **ipv4hint/ipv6hint**
содержат подсказки IP-адресов. Живой тест проверяет, что запрещённые подсказки
блокируются, а разрешённые записи сохраняются.

## Правила и IP

### IP, IPv4, IPv6, октет и 16-битная группа

**IP — Internet Protocol**; IP-адрес обозначает сетевой адрес интерфейса.
**IPv4** имеет 32 бита и обычно записывается четырьмя числами от 0 до 255;
каждое такое число — **октет**, восемь бит. **IPv6** имеет 128 бит: восемь
16-битных шестнадцатеричных групп. В записи IPv6 `::` сокращает подряд идущие
нулевые группы. Компилятор правил учитывает это сокращение.

### CIDR, сеть, префикс и маска

**CIDR — Classless Inter-Domain Routing**, запись диапазона через адрес и длину
общего префикса. `103.177.238.0/23` включает адреса от `103.177.238.0` до
`103.177.239.255`, всего 512. `/24` у IPv4 содержит 256 адресов, `/32` — один;
у IPv6 один адрес обозначается `/128`. **Маска** описывает ту же границу между
общей сетевой частью и изменяемой частью адреса.

### Публичные, приватные, reserved и multicast адреса

**Публичный адрес** предназначен для глобальной адресации. **Приватные адреса**,
например `10.0.0.0/8`, используются внутри сетей. **Reserved** — зарезервированные
адреса специального назначения. **Multicast** — групповая доставка нескольким
получателям. `validate_public_network()` проверяет первый и последний адреса
диапазона и отклоняет неподходящие границы; это не географическая проверка.

### DNS-фильтрация, IP-фильтрация ответа и firewall

**DNS-фильтрация** в проекте проверяет имя запроса и IP внутри ответа.
**Firewall** — сетевой экран, который разрешает или запрещает сетевые пакеты.
Наша сборка не добавляет правила firewall. Если приложение подключается к IP
напрямую, не обращаясь к нашему DNS, один `combined.txt` такое соединение не остановит.

### Blocklist, allowlist, правило и scope

**Blocklist** — список запрещающих правил; **allowlist** — разрешающие исключения.
**Правило** — условие совпадения и действие, а не обязательно один домен или IP.
**Scope** — область действия доменного правила в CSV: `exact` — ровно имя,
`subdomains` — только потомки, `suffix` — имя вместе с потомками.
Например, исключение для `yastatic.net` не должно разрешать все трекеры Яндекса.

### Wildcard, суффикс, IDNA и PSL

**Wildcard** — шаблон со звёздочкой: `*.example.org` описывает поддомены.
**Суффикс имени** — его правая часть, например `example.org` в `a.example.org`.
**IDNA — Internationalized Domain Names in Applications**, представление имён
с не-ASCII символами в совместимой ASCII-форме: `пример.рф` преобразуется в `xn--…`.
**PSL — Public Suffix List** перечисляет общие суффиксы вроде `co.nz` и `github.io`.
Проект использует закреплённый файл `config/public_suffix_list.dat`, чтобы
не принимать доменное правило, запрещающее целую общую платформу.

### Regex, якоря и запись отдельного IP

**Regex — regular expression, регулярное выражение**: шаблон для сопоставления
строки. В AdGuard `/.../` обозначает regex, `^` — начало, `$` — конец строки,
`\.` — буквальную точку, `(?:8|9)` — вариант 8 или 9, `[0123456789]` — одну цифру.
Так начало `103\.177\.23(?:8|9)\.` описывает `103.177.238.` или `103.177.239.`;
оставшаяся часть правила ограничивает последнее число диапазоном 0..255.
Якоря не дают принять имя `103.177.238.42.example.org` за сам IP.
Отдельный IP выводится как `|1.14.192.95|`; символы `|` фиксируют границы совпадения.

### Формат AdGuard, ABP и hosts

**ABP** в обсуждении синтаксиса — семейство правил Adblock Plus: `||`, `^`, `@@`
и модификаторы. В AdGuard `@@` обозначает исключение; например, `@@|yastatic.net^`.
**Hosts-формат** связывает IP с именем, например `0.0.0.0 ads.example.org`.
Наш парсер принимает только поддерживаемые доменные формы. Браузерное условие
`$third-party` зависит от стороннего запроса на странице, а `$domain` — от
контекста страницы; обычный DNS этого контекста не видит. Такие строки не
превращаются нашим парсером в безусловный запрет.

### null_ip, ложная блокировка и общий IP

**null_ip** — используемый тестами режим AdGuard: блокировка A возвращает
`0.0.0.0`, AAAA — `::`. Это отличается от NXDOMAIN. **Ложная блокировка** —
запрет допустимого ресурса. Несколько сайтов могут использовать **общий IP**,
поэтому IP-правило действует на адрес независимо от имени. Точное доменное
исключение в AdGuard может разрешить ответ для проверенного имени.

## Источники и категории

### Mullvad, HaGeZi, TIF и Spamhaus

**Mullvad** — VPN-провайдер и автор исходного репозитория `mullvad/dns-blocklists`.
Его DNS-списки можно использовать отдельно от VPN-клиента. **HaGeZi** — проект
списков фильтрации; **TIF — Threat Intelligence Feeds**, его набор данных об угрозах.
Наш профиль получает домены `adblock/tif.txt` и адреса `ips/tif.txt`.
**Spamhaus** — организация, публикующая данные о сетях, связанных со злоупотреблениями.
Точные источники и условия записаны в [SOURCES.md](SOURCES.md).

### DROP, SBL, RIR и ASN

**DROP — Don't Route Or Peer**, сетевые списки Spamhaus. Мы используем IPv4/IPv6
CIDR, преобразуя их в DNS-правила. **SBL — Spamhaus Block List**; `sblid` —
идентификатор записи расследования. Разные SBL могут ссылаться на одну сеть.
**RIR — Regional Internet Registry**, региональный регистратор адресов;
поле `rir` не определяет страну жертвы. **ASN — Autonomous System Number**, номер
автономной сети, например AS32934. Сам по себе ASN или страна не означает вредоносность.

### Feed, IoC, last_seen и историческое наблюдение

**Feed** — регулярно предоставляемый источник данных, например список HaGeZi.
**IoC — Indicator of Compromise**, индикатор, связанный с расследованием угрозы:
домен, IP или другой признак. **last_seen** — когда активность наблюдалась последний раз.
Дата скачивания списка не заменяет last_seen. Историческое наблюдение означает,
что признак был обнаружен в прошлом; само по себе оно не подтверждает текущую активность.

### Реклама, трекеры, malware, phishing, scam и gambling

**Реклама (adblock)** — рекламные ресурсы. **Трекеры (privacy)** — ресурсы,
собирающие данные о действиях пользователя. **Malware** — вредоносное ПО и
связанная инфраструктура. **Phishing** — обман для кражи данных, например пароля;
**scam** — мошеннические схемы. **Gambling** — азартные игры; наличие в этой
категории не является утверждением о malware. Категории **adult** (взрослый контент)
и **social** (социальные сети целиком) в профиль не включены. Реклама внутри
такого сайта может блокироваться как реклама.

### OISD, Frellwit, EasyPrivacy и AdGuard Filters

Проекты списков, которые встречаются среди источников исходной сборки Mullvad.
Это не дополнительные DNS-серверы на VPS. Наш сборщик получает готовые результаты
выбранных категорий Mullvad; их исходные преобразования уже выполнены upstream.
Браузерные RU AdList/Cyrillic используются как источники исследования,
а не автоматически исполняемые списки DNS-правил.

### CDN

**CDN — Content Delivery Network**, распределённая сеть доставки файлов сайта.
Один общий CDN обслуживает много независимых ресурсов. Блокировка всей его зоны
может нарушить работу обычных страниц; PSL и точные исключения помогают ограничить
доменные правила. Cloudflare также может выступать обратным прокси: принимать
клиентское соединение и передавать его серверу.

## Файлы и сборка

### Репозиторий, каталог, модуль и скрипт

**Репозиторий** хранит файлы проекта и их Git-историю. **Каталог** группирует файлы.
**Python-модуль** — файл, который можно импортировать; **скрипт** выполняет задачу
при запуске. Например, `pipeline.py` можно запускать с CLI-командой и импортировать
из тестов. Назначение каждого каталога описано его `README.md`.

### Сборщик, сборка и артефакт

**Сборщик** — наш код `scripts/ru/`, который проверяет источники и преобразует их
в итоговый формат. **Сборка** — один запуск этого процесса. **Артефакт** —
полученный файл, например `output/adguard/combined.txt`. Это не отдельная служба.
Наличие файла после записи ещё не доказывает успешность живых DNS-проверок.

### combined.txt

Единый фильтр AdGuard в `output/adguard/`: доменные правила, точные IP и regex
для CIDR. Комментарии с `!` содержат заголовок и уведомления источников.
Одна строка правила сети может охватывать много IP, поэтому число правил
не равно числу всех адресов, которые могут быть заблокированы.

### manifest.json и SHA256

**Манифест** `output/adguard/manifest.json` описывает выпуск: источники, количества,
категории, исключения и контрольную сумму `combined.txt`. **SHA256** — вычисляемая
по байтам контрольная сумма. Изменение файла меняет сумму и обнаруживается
сравнением с манифестом. Совпадение суммы не доказывает отсутствие malware;
если изменить и файл, и ожидаемую сумму, нужна отдельная проверка доверия к источнику.
AdGuard читает `combined.txt`, а манифест — наши инструменты.

### enforcement, dns_response и observation_only

`enforcement` — поле манифеста или записи, задающее разрешённый способ применения
данных. `dns_response` означает использование при проверке IP в DNS-ответах.
`observation_only` означает справочное наблюдение без автоматической блокировки.
Общий манифест использует поле `ip_enforcement`; сборщик проверяет ожидаемые
значения до включения данных в фильтр.

### GPG и цифровая подпись

**GPG — GNU Privacy Guard**, программа шифрования и проверки цифровых подписей.
Файл `.gpg` может содержать разные виды данных; расширение само по себе не
доказывает, что внутри зашифрованный текст. **Отдельная цифровая подпись** хранится
без подписанного файла и проверяется вместе с ним с помощью открытого ключа.
Она позволяет обнаружить изменение данных и установить использованный ключ;
доверие к владельцу ключа проверяется отдельно.

### Поля манифеста и даты

`rule_count` — суммарное число правил, `domain_rule_count` — доменных,
`ip_rule_count` — адресных/сетевых. `sources` и `ip_sources` описывают источники.
`upstream_commit` фиксирует версию Mullvad. `retrieved_at` означает получение
данных, `commit_at` — время commit источника, `source_published_at` — время
публикации в метаданных DROP. Поле общего манифеста `verified_at` заполняется
временем получения доменного lock; оно не является временем последнего live-теста.
Ни одна из этих дат не подменяет индивидуальное last_seen.

### Снимок, lock-файл и кэш сборки

**Снимок** — конкретные байты источника на фиксированной версии. **Lock-файл**
`.cache/feeds/lock.json` связывает идентификаторы источников с именами файлов,
commit SHA, датами и SHA256. Для IP используется `ip-lock.json`.
**Кэш сборки** `.cache/` хранит скачанные данные и инструменты; его нельзя путать
с кэшем DNS-ответов или внутренней копией фильтра в AdGuard.

### JSON, JSON Lines, CSV, YAML и Markdown

**JSON** хранит объекты, массивы и значения: так записаны манифесты.
**JSON Lines (JSONL)** содержит отдельный JSON-объект на каждой строке;
у DROP последняя строка — metadata. **CSV** — таблица с разделителями, используемая
для региональных доменов и исключений. **YAML** — формат конфигурации workflows. **Markdown (MD)** — текст с заголовками, списками и ссылками, например этот файл.

### ASCII, UTF-8, BOM и LF

**ASCII** — базовая кодировка латинских символов, цифр и знаков; IDNA переводит
международные доменные имена в совместимую ASCII-запись. **UTF-8** кодирует Unicode,
включая русский текст. **BOM** — возможная метка кодировки в начале файла;
`utf-8-sig` учитывает её при чтении. **LF** — символ переноса строки, который
использует atomic_write при записи воспроизводимых текстовых файлов.

### Дедупликация, детерминированность и атомарная запись

**Дедупликация** удаляет повторы. **Детерминированная сборка** даёт одинаковые байты
при одинаковых входах. **Атомарная запись** в нашем коде сначала сохраняет временный
файл и заменяет им целевой: читатель не получает половину одного файла.
Это не делает замену нескольких файлов одной общей транзакцией.

### Лицензия, GPL, MPL и уведомление источника

**Лицензия** задаёт условия использования и распространения. Для кода и применимых
списков используется **GPL-3.0 (GNU General Public License)**, у PSL —
**MPL-2.0 (Mozilla Public License)**. Данные Spamhaus имеют собственные условия.
Название источника, copyright и terms сохраняются при преобразовании;
добавление данных в наш файл не делает их автоматически GPL. См. [SOURCES.md](SOURCES.md).

## Git и GitHub Actions

### Git, GitHub, fork и upstream

**Git** хранит версии файлов; **GitHub** размещает Git-репозитории и автоматические
задания. **Fork** — связанная копия чужого репозитория на GitHub.
Наш fork — `bakzalitdootvala/dns-blocklists-ru`, **upstream** — исходный
`mullvad/dns-blocklists`. Это не upstream DNS, которому отправляют DNS-запросы.

### Ветка, main, maintainer, origin и remote

**Ветка** — именованный указатель на линию Git-истории. **main** содержит наш профиль
и код. **maintainer** служит чистой копией upstream main. **Remote** — именованное
подключение к удалённому репозиторию; **origin** указывает на наш fork, **upstream** —
на Mullvad. Изменение локального файла само по себе не меняет GitHub.

### Commit, commit SHA, push и fast-forward

**Commit** фиксирует набор изменений в истории. **Commit SHA** — его идентификатор;
он отличается от SHA256 содержимого `combined.txt`. **Push** отправляет коммиты
и обновляет ветку на удалённом сервере. **Fast-forward** продвигает ветку по прямому
продолжению истории без переписывания существующих коммитов.
`sync_upstream.py` использует этот принцип и запрещает force при расхождении.

### Pull request, CI и workflow

**Pull request (PR)** — предложение включить изменения в ветку.
**CI — Continuous Integration**, автоматические проверки изменений.
**Workflow** — YAML-файл задания GitHub Actions с условиями запуска и шагами.
У нас `ru-checks.yml` проверяет код и готовый файл,
`update-lists.yml` получает, собирает, проверяет и публикует данные.
Подробное сравнение: [README workflows](../.github/workflows/README.md).

### Job, step, runner, name, uses и run

**Job** — группа шагов на одной машине исполнения; **step** — один шаг.
**Runner** — машина, на которой GitHub выполняет job; это не VPS пользователя.
**name** — видимое человеку название. **uses** вызывает готовое действие,
например `actions/checkout` получает файлы репозитория. **run** выполняет команды.
Суффикс `@<SHA>` закрепляет действие на конкретном commit его кода.

### schedule, cron, workflow_dispatch и concurrency

**schedule** задаёт расписание; **cron** — его текстовая запись. `23 6 * * *`
означает каждый день в 06:23 UTC, то есть 09:23 по Москве; это время планирования,
а не обещание старта ровно в секунду. **workflow_dispatch** разрешает ручной запуск.
**Concurrency** ограничивает одновременные выполнения; группа публикации
не позволяет двум нашим заданиям обновлять main одновременно.

### env, GH_TOKEN, github.token, secrets и permissions

**env** задаёт переменные окружения процесса. **GH_TOKEN** — переменная, из которой
GitHub CLI берёт токен доступа к API. **github.token** GitHub создаёт для запуска
workflow; для этого не нужен локальный `.env`. **Secrets** — защищённые настройки
секретов; реальные значения не хранятся в публичном YAML. **Permissions** ограничивает
права токена: например, `contents: read` для проверки и `write` для публикации.

### API, CLI, gh и github-actions[bot]

**API — Application Programming Interface**, программный способ обращаться к сервису.
**CLI — Command-Line Interface**, интерфейс командной строки. **gh** — GitHub CLI,
который наши скрипты используют для API GitHub. **github-actions[bot]** — служебное
имя автора автоматических коммитов. Автор коммита и аккаунт, которым авторизован
сетевой push, — разные понятия; локальные имя/email не доказывают аккаунт отправителя.

## Проверки и инструменты

### Unit-тест, интеграционный тест, fixture и mock

**Unit-тест** проверяет отдельное поведение функции. **Интеграционный тест** проверяет
взаимодействие частей, например вызов сборщика с реальными временными файлами.
**Fixture** — подготовленные тестовые данные или сервис с известными ответами.
**Mock** — подмена внешнего вызова контролируемым результатом. Наши unit-тесты
не отправляют изменения GitHub; сетевые вызовы там подменены.

### Живая DNS-проверка и контрольные домены

**Живая проверка** запускает настоящий AdGuard и получает DNS-ответы по сети.
`test_ip_response.py` возвращает из тестового DNS известный запрещённый IP,
а затем проверяет, что AdGuard его отфильтровал. **Контрольные домены** из
`config/controls.json` имеют ожидаемый результат: allowed либо blocked.
Это выбранные сценарии, а не проверка всех страниц, входов и покупок в интернете.

### Мутационная проверка

Намеренное изменение защищаемого поведения, которое тест должен обнаружить.
Например, отключение фильтрации должно вернуть исходный IP и нарушить ожидание
блокировки. После восстановления проверки снова проходят. Это помогает отличить
реальный тест от проверки, которая остаётся зелёной при сломанной функции.

### dig — отправка DNS-запроса из терминала

**dig — Domain Information Groper**, утилита для обращения к DNS-серверу и просмотра
его ответа. Она позволяет проверить DNS отдельно от браузера: какое имя спросили,
у какого сервера, какой тип записи запросили и что получили. В Ubuntu входит
в пакет `dnsutils`. Это клиент проверки; он не запускает DNS-сервер и не меняет фильтры.

Например, команда `dig @127.0.0.1 -p 5353 example.org A` спрашивает IPv4-адрес
`example.org` у DNS-сервера на этой же машине, слушающего порт 5353:

- `@127.0.0.1` — адрес опрашиваемого DNS-сервера; это не адрес сайта.
- `-p 5353` — порт DNS-сервера; без этого параметра обычно используется 53.
- `example.org` — запрашиваемое имя, `A` — тип записи IPv4; `AAAA` запрашивает IPv6.
- `status: NOERROR` в выводе означает, что запрос обработан без DNS-ошибки.
  Это ещё не доказывает доступность сайта: ответ может не содержать нужной записи.
- `ANSWER SECTION` содержит полученные записи. В нашем режиме блокировки A
  возвращает `0.0.0.0`, AAAA — `::`; обычный ответ содержит разрешённый адрес.
- `SERVER` показывает, какой сервер ответил, `Query time` — время запроса
  в миллисекундах. Это не измерение скорости загрузки сайта.

`+short` сокращает вывод, но скрывает важные сведения, включая DNS-статус.
Поэтому `scripts/ru/verify_adguard.py` использует `+noall +comments +answer`:
оставляет статус и записи и проверяет A/AAAA отдельно. Для живого тестового
AdGuard выбирается его отдельный порт; команда выше должна выполняться на машине,
где действительно работает указанный DNS-сервис. Соединение с самим сайтом dig
не устанавливает, но DNS-сервер может обратиться к внешним серверам за ответом.

### Ruff, unittest, Gitleaks и actionlint

**Ruff** проверяет ошибки и
формат Python. **unittest** запускает тесты стандартной библиотекой Python.
**Gitleaks** ищет признаки секретов в файлах; это не антивирус. **actionlint**
проверяет структуру GitHub workflows. Эти инструменты проверяют разные свойства.

### requests, subfinder, apt и dnf

**requests** — сторонняя Python-библиотека HTTP-запросов. **subfinder** — инструмент
поиска поддоменов. Наш сборщик использует стандартную библиотеку Python.
**apt** и **dnf** — менеджеры установки системных пакетов: apt применяется в Ubuntu,
dnf — в Fedora и совместимых системах. Наши workflow используют apt для установки
ClamAV и DNS-утилит на машине GitHub.

### Pre-commit hook и lifecycle hook

**Hook** — действие на заданное событие. **Pre-commit hook** запускается перед
созданием Git-коммита и может остановить его при ошибке проверки.
**Lifecycle hook** относится к событиям работы агента; он не является Git-хуком
и не даёт разрешения на commit/push. Состав pre-commit хранится в
`.pre-commit-config.yaml`; его расширение требует согласования владельца.

### ClamAV, сигнатура, freshclam и clamscan

**ClamAV** — антивирус. **Сигнатуры** описывают признаки известных угроз;
**freshclam** обновляет их базу, **clamscan** проверяет файлы. В цепочке проекта
скачанный DROP проверяется до разбора JSON, загруженные инструменты — до запуска.
Чистый результат не доказывает абсолютную безопасность и не заменяет SHA256,
проверку источника, структуры и содержимого.

## Сервер и эксплуатация

### VPS, Ubuntu LTS, root и обычный пользователь

**VPS — Virtual Private Server**, виртуальный сервер. **Ubuntu** — операционная
система Linux; **LTS — Long Term Support**, выпуск с длительной поддержкой.
**root** — административная учётная запись. Обычный пользователь имеет ограниченные
права; root нужен для системных конфигов и служб. Секреты и конкретные настройки
доступа к VPS не входят в публичные файлы проекта.

### SSH, порт, TCP, UDP и loopback

**SSH — Secure Shell**, защищённый удалённый доступ. **Порт** — номер сетевой
службы на адресе. **TCP** передаёт упорядоченный поток данных через соединение,
**UDP** передаёт отдельные датаграммы. DNS может использовать оба транспорта.
**Loopback** — адрес самого компьютера, например `127.0.0.1`; тестовый AdGuard
слушает только его, чтобы API без пароля не был доступен извне.

### systemd, daemon, Docker и UFW

**systemd** управляет системными службами Linux. **Daemon (демон)** — работающий
в фоне процесс службы. **Docker** запускает процессы в контейнерах с отдельными
настройками среды и ограничениями. **UFW — Uncomplicated Firewall**, инструмент
управления сетевым экраном Linux. Наши списки IP не загружаются в UFW.

### Xray, Hysteria, REALITY, WebSocket и Cloudflare

**Xray** и **Hysteria** — отдельные программы прокси-соединений. Они не являются
форматами блоклистов. **REALITY** — механизм защиты соединений, используемый Xray;
**WebSocket** — транспорт двустороннего обмена через HTTP-совместимое соединение.
**Cloudflare** может принимать это соединение и передавать его на сервер.
Фильтр действует на запросы, которые действительно проходят через наш DNS;
наличие прокси не гарантирует, что приложение не использует собственный DNS.

### Relay

**Relay** в контексте VPN — серверный узел, через который передаётся трафик клиента.
Списки категории Mullvad для таких узлов сборщик скачивает по удалённым путям
`output/relay/`, заданным в `config/sources.json`. Результат для AdGuard хранится
в `output/adguard/combined.txt`.

### Backup, rollback, RSS и SIGTERM

**Backup** — резервная копия для восстановления.
**Rollback** — возврат рабочего состояния из совместимого комплекта конфигурации, исходного фильтра и его кэша.
**RSS — Resident Set Size**, объём физической памяти процесса; пиковое значение помогает оценить загрузку полного списка.
**SIGTERM** — сигнал завершения процесса; тестовый стенд обрабатывает его так, чтобы остановить дочерний AdGuard и освободить порты.

### multipath

Подсистема Linux для нескольких путей доступа к одному устройству хранения.
Сообщение о ней в журнале само по себе не доказывает отказ обычного диска VPS;
состояние диска проверяется отдельно. К сборке `combined.txt` эта подсистема не относится.
